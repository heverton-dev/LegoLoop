### Sugestão Técnica: O Modelo Híbrido (*Dual-Role*)

A melhor abordagem técnica para o LegoLoop é adotar o **Modelo Híbrido**:

#### 1. Ativo Canônico Único (SSOT no Inventário)
Qualquer Gate, Script ou Hook vive no acervo como uma peça autônoma reutilizável (em `~/.aidd/canonical/` ou no diretório do projeto). Uma peça de gate (ex.: `gate-unit-tests.json` ou `gate-schema-validator`) é uma unidade atômica independente de onde ela é encaixada.

#### 2. Consumo Flexível no Grafo
Permitir que a mesma peça seja consumida de duas formas:

1. **Inline / Slot (Micro-escopo):**
   * Configurada em `slots` dentro de um nó.
   * **Vantagem:** Evita poluir o canvas visual com dezenas de micro-validações triviais.
2. **First-Class DAG Node (Macro-escopo):**
   * Promover `NodeType` para suportar `gate` nativo (`TypeGate NodeType = "gate"`).
   * Possui `id`, `depends_on`, entra no DAG e tem renderização visual própria no canvas.
   * **Vantagem:** Dá visibilidade explícita a marcos críticos (ex.: **Stop-Gates de Aprovação Humana**, bifurcações condicionais `pass/fail` e gates de homologação).

### Resumo da Recomendação
* **Curto prazo:** Manter Gates e Hooks em `slots` para proteções locais do nó, mas elevar **Gate a nó externo de 1ª classe no DAG** quando ele representar um ponto de parada, decisão ou aprovação entre etapas.
* **Longo prazo:** Manter o princípio: *a peça no disco é sempre autônoma; o desenvolvedor decide no canvas se ela encaixa dentro de outro bloco (slot) ou na esteira principal (nó).*

### 2. Governança de Slots de Peças Canônicas (Ex.: Peças do Loop Impeccable)

Para peças canônicas do sistema (não criadas pelo usuário), a regra de ouro é **Imutabilidade Canônica com Extensibilidade** (padrão *Copy-on-Write*).

A edição direta da peça original no acervo canônico **não deve ser permitida**, pois causaria:
1. Perda de customizações em atualizações do sistema/pack.
2. Quebra de integridade em outros loops que dependem daquela mesma peça.

#### Mecanismos Recomendados:

#### A. Fork / Clonar Peça (Novo Ativo no Projeto)
* **Como funciona:** O usuário clica em "Fork" ou "Duplicar Peça". O LegoLoop clona a definição para o escopo do projeto (`.legoloop/components/...`) ou do usuário.
* **Resultado:** O usuário tem controle irrestrito: remove/adiciona gates, altera scripts, troca MCPs e ajusta prompts sem afetar a peça canônica original.

#### B. Slot Override no Pipeline (Sem clonar arquivo)
* **Como funciona:** O usuário usa a peça canônica original no nó, mas declara uma sobreposição pontual apenas naquele pipeline:
  ```json
  {
    "id": "design-pass",
    "ref": "impeccable/design-review",
    "slots_override": {
      "remove_gates": ["gate-strict-contrast"],
      "add_scripts": [["npm", "run", "lint:css"]]
    }
  }
  ```
* **Resultado:** Mantém a peça atualizada com as melhorias upstream do LegoLoop, aplicando apenas as customizações estritamente necessárias para aquele projeto específico.

### Síntese
* **Outras peças:** Skills, MCPs e Binários operam perfeitamente no modelo híbrido; apenas **Subloops** devem permanecer estritamente como nós externos.
* **Customização de Slots:** Peças canônicas são **somente leitura**. O usuário customiza via **Override no DAG** (para pequenos ajustes locais) ou via **Fork da Peça** (quando deseja criar uma variação própria permanente).
